# Целевая интеграционная архитектура «Здоровье+» (C4 Level 1)

Документ описывает целевой ИТ-ландшафт «Здоровье+» для запуска мобильного приложения пациента. Он опирается на анализ текущей архитектуры (см. `Task1/problems.md`, далее ссылки вида **П-N** указывают на номер проблемы из этого анализа) и задаёт интеграционные паттерны, архитектурные стили и потоки данных, которые закрывают выявленные проблемы и позволяют достичь целевых показателей: MVP через 3 месяца (500 одновременных пользователей), финальное решение через год (50 000 пользователей в пик, отклик < 1 с для 99 % запросов, доступность 99,95 %, горизонтальное масштабирование всех компонентов).

Исходник диаграммы: [target-context.puml](target-context.puml).

## 1. Принципы целевой архитектуры

| № | Принцип | Какие проблемы закрывает |
|---|---|---|
| 1 | **Единая точка входа для внешних клиентов.** Мобильное приложение и веб-портал обращаются к бэкенду только через API Gateway. Прямые вызовы клиентами систем расписания, 1С и платёжного шлюза запрещены. | П-1, П-5, П-10, П-11 |
| 2 | **Синхронно только там, где пользователю нужен немедленный ответ и важна строгая согласованность (CP).** Резерв слота, проведение платежа, проверка полиса на критическом пути записи. | П-3, П-4 |
| 3 | **Асинхронно везде, где допустима итоговая согласованность (AP).** Уведомления, синхронизация CRM, доставка результатов анализов, обновление полисов в 1С. Бизнес-события публикуются в брокер через transactional outbox. | П-7, П-8, П-9 |
| 4 | **Легаси-системы изолируются адаптерами (Anti-Corruption Layer).** 1С и LIS не вызываются напрямую: перед ними стоят сервисы, которые владеют контрактом, кэшем, таймаутами, повторами и Circuit Breaker. | П-5, П-6, П-7 |
| 5 | **Бизнес-операция «запись + оплата + лаборатория» выполняется как оркестрируемая Saga с компенсациями.** Промежуточные состояния не остаются «висеть»: слот освобождается, платёж возвращается, резерв в лаборатории снимается. | П-3, П-4 |
| 6 | **Идемпотентность на входе и на каждом шаге.** Клиент передаёт `Idempotency-Key`, API Gateway и сервис записи дедуплицируют повторы, платёжный сервис использует идемпотентный ключ шлюза. | П-1, П-3 |
| 7 | **Разделение чтения и записи для «горячих» данных.** Поиск слотов идёт в реплику чтения и кэш, запись — в мастер с оптимистичной блокировкой. | П-2, П-13 |
| 8 | **Наблюдаемость по умолчанию.** Каждый запрос получает `trace-id` на API Gateway и прокидывается через все вызовы и события (OpenTelemetry). | П-12 |
| 9 | **Безопасность на периметре.** OAuth 2.0 / OIDC, короткоживущие JWT, TLS 1.2+, валидация входных данных на API Gateway, RBAC и проверка принадлежности данных пациенту. | П-11 |
| 10 | **Эволюция без «большого взрыва» (Strangler Fig).** Веб-портал переводится на API Gateway постепенно, существующие системы расписания, CRM, LIS и 1С сохраняются, меняется только способ интеграции с ними. | П-10, П-13 |

| Элемент | Статус | Назначение в целевой архитектуре | Закрывает |
|---|---|---|---|
| **Мобильное приложение** | Новый | Основной канал пациента: запись, оплата, результаты анализов, полисы ДМС, push. Работает только через API Gateway и Identity Provider. | Цели бизнеса |
| **API Gateway** | Новый | Единая точка входа: терминирование TLS, проверка JWT, rate limiting (в том числе для защиты 1С и расписания), дедупликация по `Idempotency-Key`, версионирование `/api/v1`, маршрутизация и агрегация, генерация `trace-id`. | П-1, П-5, П-10, П-11, П-12 |
| **Identity Provider** | Новый | OAuth 2.0 / OIDC: выпуск access/refresh-токенов, MFA, отзыв, RBAC (пациент, врач, администратор). Убирает самодельные сессии портала. | П-11 |
| **Сервис записи (оркестратор Saga)** | Новый | Владелец бизнес-операции «запись к врачу с оплатой и резервированием лаборатории». Хранит состояние Saga, выполняет компенсации, публикует события через transactional outbox. | П-3, П-4 |
| **Сервис полисов (ACL + кэш)** | Новый | Anti-corruption layer над 1С: единственный клиент 1С, кэш полисов, ограничение частоты вызовов, Circuit Breaker, очередь команд на изменение полисов, ночная синхронизация реестра. | П-5, П-6, П-13 |
| **Платёжный сервис** | Новый | Единственный клиент платёжного шлюза: идемпотентные операции, хранение статусов платежей, приём webhook, регулярная сверка с реестром шлюза, инициирование возвратов. | П-3, П-4 |
| **Сервис результатов анализов** | Новый | Заменяет Perl-коннектор LIS → CRM. Принимает результаты из LIS с повторами, дедуплицирует по идентификатору результата, хранит витрину результатов для пациентов, публикует событие `LabResultReady`. | П-7, П-8 |
| **Брокер событий (Apache Kafka)** | Новый | Шина доменных событий с гарантией at-least-once, хранением (retention) и DLQ. Развязывает сервис записи, платежи, результаты анализов, CRM и уведомления. | П-7, П-9, П-13 |
| **Платформа наблюдаемости** | Новый | Сбор трасс, метрик и логов по OpenTelemetry со всех новых и существующих компонентов; алерты по SLO. | П-12 |
| **Расписание** | Существующий, дорабатывается | Добавляются реплика чтения для поиска слотов, резерв слота с TTL (двухфазная запись), оптимистичная блокировка, поддержка `Idempotency-Key`. | П-1, П-2, П-13 |
| **CRM** | Существующий | Становится потребителем событий (карточка, история обращений, результаты анализов) вместо синхронной синхронизации из портала. | П-7 |
| **LIS** | Существующий | Остаётся источником результатов; загрузка с анализаторов по FTP переводится под мониторинг и автоматические повторы. Интеграция наружу — через сервис результатов анализов. | П-7 |
| **1С: Полисы** | Существующий | Остаётся системой учёта полисов, но вызывается только сервисом полисов с ограничением нагрузки. | П-5 |
| **Уведомления** | Существующий, модернизируется | RabbitMQ переводится в кластер с квотами, TTL и DLQ. Источник событий — Kafka, а не прямые вызовы портала. | П-9 |
| **Веб-портал** | Существующий | Переводится на API Gateway по принципу Strangler Fig; прямые вызовы бэкендов выводятся из эксплуатации. | П-10 |
| **Платёжный шлюз, провайдеры push/SMS/e-mail** | Внешние | Без изменений; меняется способ интеграции (идемпотентность, webhook, сверка, повторы). | П-3, П-9 |

## 3. Интеграции: выбор паттернов и обоснование

Для каждой новой интеграции выбор сделан по трём инструментам: **дерево принятия решений** (нужен ли немедленный ответ → могут ли данные ждать часы → сколько потребителей), **CAP-теорема** (что критичнее для бизнеса в сценарии: строгая согласованность или непрерывность приёма запросов) и **критерии стиля** (задержка, связанность, консистентность, инфраструктура, обратная связь).

| № | Интеграция | Стиль взаимодействия | CAP | Почему выбран этот паттерн |
|---|---|---|---|---|
| И-1 | Мобильное приложение → **API Gateway** | Синхронный REST/HTTPS (JSON), `Authorization: Bearer JWT`, `Idempotency-Key` на всех POST/PUT | CP на запись, AP на чтение (кэш) | Дерево: пользователю нужен немедленный ответ, получатель (шлюз) всегда доступен за счёт горизонтального масштабирования → синхронный вызов. Единственная точка, где централизованно решаются аутентификация, rate limiting, идемпотентность и версионирование (П-1, П-10, П-11). |
| И-2 | Мобильное приложение → **Identity Provider** | Синхронный OAuth 2.0 Authorization Code + PKCE, OIDC | CP | Выдача токена без немедленного ответа невозможна; стандартный протокол убирает самодельные сессии (П-11). Refresh-токены позволяют не хранить пароль на устройстве. |
| И-3 | API Gateway → **Identity Provider** | Синхронная проверка подписи JWT по JWKS с локальным кэшем ключей; интроспекция только для отзыва | CP с деградацией в AP | Проверка каждого запроса не должна зависеть от доступности IdP: подпись проверяется локально, ключи кэшируются. |
| И-4 | API Gateway → **Расписание** (поиск врачей и слотов) | Синхронный REST в реплику чтения + кэш с TTL 5–15 с (CQRS-чтение) | AP | Самая частая операция приложения. Немедленный ответ нужен, но устаревание списка слотов на секунды допустимо: окончательная проверка делается при резерве. Так снимаются блокировки таблицы слотов (П-2) и выполняется требование отклика < 1 с при 50 000 пользователей. |
| И-5 | API Gateway → **Сервис записи** (создать/отменить запись) | Гибрид: синхронный приём запроса (`202 Accepted`, идентификатор Saga) + асинхронное завершение (опрос статуса и push) | CP на каждом шаге Saga, итоговая согласованность операции в целом | Дерево: немедленный ответ нужен, но получатели (1С, платёжный шлюз, LIS) не всегда доступны → «синхронный запрос с fallback на асинхронный». Пользователь сразу видит статус «Обрабатывается», а не зависание на 10 с (SD-004). |
| И-6 | Сервис записи → **Расписание** (резерв, подтверждение, освобождение слота) | Синхронный REST, резерв с TTL, идемпотентный ключ шага, оптимистичная блокировка | CP | Слот — разделяемый ресурс: два пациента не должны занять одно время. При недоступности расписания запись честно отклоняется, а не создаётся «в надежде» (принцип: точность важнее непрерывности). Закрывает дубли (П-1). |
| И-7 | Сервис записи → **Сервис полисов** → **1С** (проверка полиса) | Комбинация: синхронный REST к сервису полисов с ответом из кэша; при промахе кэша — синхронный вызов 1С с таймаутом, Circuit Breaker и ограничением частоты; при открытом Circuit Breaker — ответ из кэша с признаком «данные на момент T» | CP на шаге Saga; кэш даёт AP-деградацию с явным флагом | 1С деградирует при > 50 RPS и зависает более 30 с (П-5), поэтому прямой синхронный вызов недопустим. Кэш переводит 99 % проверок в чтение без 1С; решение «считать полис валидным без ответа» заменяется на осознанную политику: свежий кэш → пропустить, устаревший кэш → предложить оплату или подтверждение в клинике. |
| И-8 | Сервис полисов → **1С** (прикрепление полиса, обновление) | Асинхронная команда point-to-point: очередь команд с повторами и экспоненциальной задержкой, DLQ | AP | Дерево: немедленный ответ не нужен (пациент получает push «полис прикреплён»), ждать часы нельзя, потребитель один → асинхронная команда. 1С обрабатывает поток в своём темпе, всплески гасятся очередью. |
| И-9 | Сервис полисов ← **1С** (ночная выгрузка реестра) | Пакетная интеграция по расписанию | AP | Реестр полисов меняется редко, данные могут ждать часы → batch. Прогревает кэш и снижает дневную нагрузку на 1С до единичных промахов кэша. |
| И-10 | Сервис записи → **Платёжный сервис** → **Платёжный шлюз** (проведение платежа) | Комбинация: синхронный REST с жёстким таймаутом и идемпотентным ключом операции; при таймауте — не повтор списания, а синхронный запрос статуса по тому же ключу; финальный статус подтверждается webhook (асинхронный колбэк); ежедневная пакетная сверка | CP | Дубль платежа — прямые финансовые потери (П-3, SD-009), поэтому шаг оплаты строго CP: при неопределённом ответе платёж не считается ни успешным, ни проваленным до получения статуса. Колбэк даёт достоверность при задержках шлюза, сверка закрывает «потерянные» статусы (INT-001). |
| И-11 | Сервис записи → **LIS** (резерв времени забора биоматериала) | Синхронный SOAP через адаптер с таймаутом и компенсацией «снять резерв» | CP | Лабораторное время — тоже разделяемый ресурс, требуется немедленное подтверждение внутри Saga. Отдельный адаптер изолирует SOAP-контракт от остальных сервисов. |
| И-12 | Сервис записи → **Брокер событий** (`BookingConfirmed`, `BookingCancelled`) | Асинхронные события pub/sub через transactional outbox | AP | Потребителей несколько (уведомления, CRM, результаты анализов, аналитика) и они меняются независимо → pub/sub. Outbox гарантирует, что событие публикуется тогда и только тогда, когда состояние Saga зафиксировано. |
| И-13 | **LIS** → **Сервис результатов анализов** | Асинхронное событие «результат готов» с идентификатором результата (REST push от LIS; при недоступности push — опрос по расписанию), at-least-once, дедупликация по идентификатору | AP | Немедленный ответ пациенту не нужен, но задержка 2 часа недопустима → асинхронно. Дедупликация закрывает дубли XML (INT-008), повторы и опрос закрывают ручные перезапуски (INT-002, SD-005). |
| И-14 | Сервис результатов анализов → **Брокер** → **CRM** и **Уведомления** (`LabResultReady`) | Pub/sub, идемпотентный upsert в CRM | AP | Потребителей несколько (CRM, уведомления, витрина для пациентов) и они независимы → pub/sub. CRM перестаёт быть узким местом на пути к пациенту: приложение читает результаты из витрины сервиса, а не из CRM (П-8, INT-011). |
| И-15 | API Gateway → **Сервис результатов анализов** (чтение результатов пациентом) | Синхронный REST (только чтение) с проверкой принадлежности результата пациенту | CP на уровне запроса (данные уже сохранены) | Пациент ожидает немедленный ответ; сервис горизонтально масштабируется как витрина чтения. |
| И-16 | **Брокер** → **Уведомления** → провайдеры push/SMS/e-mail | Pub/sub из Kafka; внутри сервиса уведомлений — кластер RabbitMQ с квотами, TTL, DLQ; к провайдерам — асинхронно с повторами | AP | Уведомление не должно блокировать основной поток; всплеск вечером понедельника абсорбируется retention Kafka, а не переполнением RabbitMQ (П-9, SD-006). Маркетинговые рассылки идут отдельным топиком с более низким приоритетом. |
| И-17 | Веб-портал → **API Gateway** | Синхронный REST (те же API, что у приложения) | CP / AP по типу операции | Strangler Fig: портал становится ещё одним клиентом платформы, прямые вызовы бэкендов выводятся поэтапно. Врачи получают то же поведение резерва слота с оптимистичной блокировкой (П-2). |
| И-18 | Все компоненты → **Платформа наблюдаемости** | Асинхронная отправка телеметрии (OTLP, fire-and-forget) | AP (допустима потеря части телеметрии) | Телеметрия не должна влиять на бизнес-путь; корреляция по `trace-id` через синхронные вызовы и заголовки событий (П-12). |

## 4. Архитектурные стили и их роль

| Стиль | Где применяется | Почему |
|---|---|---|
| **API Gateway / Backend for Frontend** | Периметр: мобильное приложение и портал → шлюз | Централизует сквозные задачи (аутентификация, rate limiting, идемпотентность, версионирование), отделяет контракт приложения от контрактов бэкендов, позволяет поддерживать несколько версий приложения в магазинах (П-10). |
| **Микросервисы** | Сервис записи, платёжный сервис, сервис полисов, сервис результатов анализов | Каждый сервис владеет своими данными и своей интеграцией с легаси или внешней системой, масштабируется независимо и деплоится отдельно. Согласуется с уже микросервисными расписанием и CRM. |
| **Событийно-ориентированная архитектура (EDA)** | Kafka как шина доменных событий | Слабая связанность между сервисами, буферизация пиков, несколько независимых потребителей одного события, возможность добавлять потребителей (аналитика, маркетинг) без изменения источников. |
| **Оркестрируемая Saga** | Сервис записи | Бизнес-операция затрагивает 4 системы (расписание, 1С, платёжный шлюз, LIS) с обязательными компенсациями. Оркестратор даёт единое место для состояния, таймаутов и компенсаций, что упрощает эксплуатацию по сравнению с хореографией (П-4). |
| **Anti-Corruption Layer (ACL)** | Сервис полисов перед 1С, адаптеры перед LIS и платёжным шлюзом | Легаси-контракты нестабильны (1С меняет JSON на XML без уведомления, LIS на SOAP). ACL фиксирует внутренний стабильный контракт, изолирует изменения и концентрирует паттерны отказоустойчивости (П-5, П-6). |
| **CQRS на уровне данных расписания и результатов анализов** | Реплика чтения расписания, кэш слотов, витрина результатов | Чтение в разы превышает запись; разделение снимает блокировки и позволяет масштабировать чтение горизонтально (П-2, П-13). |
| **Transactional Outbox** | Сервис записи, платёжный сервис, сервис результатов анализов | Устраняет потерю событий между фиксацией состояния в БД и публикацией в брокер. |
| **Strangler Fig** | Миграция веб-портала | Позволяет запустить MVP за 3 месяца, не переписывая портал, и постепенно вывести из эксплуатации прямые вызовы. |

## 5. Как комбинируются стили в ключевых сценариях

### 5.1. Запись к врачу с оплатой и резервированием лаборатории

1. Приложение отправляет `POST /api/v1/appointments` с `Idempotency-Key`. API Gateway проверяет JWT и лимиты, дедуплицирует повтор (тот же ключ → тот же ответ) и синхронно передаёт запрос в сервис записи.
2. Сервис записи создаёт Saga и синхронно выполняет шаги: резерв слота с TTL (CP) → проверка полиса из кэша (CP с деградацией в кэш) → инициирование платежа (CP) → резерв времени в LIS (CP). Клиент получает `202 Accepted` с идентификатором операции сразу после резерва слота.
3. Финальный статус платежа приходит асинхронно webhook-ом от шлюза; при таймауте платёжный сервис запрашивает статус по идемпотентному ключу, а не повторяет списание.
4. После подтверждения всех шагов Saga фиксирует состояние и через outbox публикует `BookingConfirmed`. Уведомления отправляют push, CRM обновляет историю обращений.
5. При сбое любого шага выполняются компенсации в обратном порядке (снять резерв LIS, вернуть платёж, освободить слот) и публикуется `BookingCancelled`.

Таким образом синхронный стиль обеспечивает строгую согласованность там, где делятся ресурсы и деньги, асинхронный — доступность и развязку побочных эффектов, а колбэк и пакетная сверка закрывают неопределённость внешнего шлюза.

### 5.2. Доставка результатов анализов

1. LIS сообщает о готовности результата событием в сервис результатов анализов (push; при отсутствии push за контрольный интервал сервис опрашивает LIS сам).
2. Сервис дедуплицирует результат, сохраняет в витрину и публикует `LabResultReady` в Kafka через outbox.
3. Потребители независимы: CRM выполняет идемпотентный upsert, уведомления отправляют push «результаты готовы», аналитика считает SLA.
4. Пациент открывает результат в приложении синхронным запросом к витрине через API Gateway. CRM больше не находится на критическом пути пациента.

### 5.3. Управление полисом ДМС

1. Проверка полиса при записи — синхронно из кэша сервиса полисов; в 1С уходят только промахи кэша, ограниченные Circuit Breaker и лимитом частоты.
2. Прикрепление или обновление полиса — асинхронная команда в очередь к 1С; пациент видит статус «В обработке» и получает push по завершении.
3. Ночная пакетная выгрузка реестра поддерживает кэш актуальным и снижает дневную нагрузку на 1С.

## 7. Допущения

1. LIS предоставляет REST API для интеграции, пригодный как для push-уведомления о готовности результата, так и для опроса; резерв времени забора биоматериала доступен через SOAP-интерфейс LIS.
2. Платёжный шлюз поддерживает идемпотентный ключ операции, запрос статуса платежа по этому ключу, webhook о финальном статусе и выгрузку реестра операций для сверки.
3. Приложение работает как отдельный клиент OAuth 2.0; учётные записи пациентов мигрируют из существующей базы портала в Identity Provider.
4. Бизнес согласовывает политику проверки полиса при недоступности 1С (свежесть кэша, при которой полис считается подтверждённым, и сценарий предложения оплаты при устаревшем кэше).
5. Изменение внутренней загрузки LIS с анализаторов по FTP не входит в объём интеграционной архитектуры и решается на стороне LIS (мониторинг и автоматические повторы).
