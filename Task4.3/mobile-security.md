# Базовые меры безопасности мобильного приложения «Здоровье+»

## 1. Схема аутентификации пациента

Схема: [`auth-flow.puml`](auth-flow.puml).

**Протокол.** OAuth 2.0, поверх — OpenID Connect. Мобильное приложение — публичный клиент: секрет в него не встраивается. Собственная схема сессий не используется — именно она причина SD-007.

**Вход.** Учётные данные пациент вводит на странице входа Identity Provider, приложение их не обрабатывает и не хранит. Второй фактор — одноразовый код в SMS. Приложение заранее генерирует `code_verifier` и передаёт в запрос его хеш `code_challenge = S256(code_verifier)`, поэтому перехваченный на устройстве авторизационный код бесполезен.

**Токены.**

| Токен | Формат и срок | Хранение |
|---|---|---|
| `access_token` | JWT RS256, TTL 15 минут. Claims: `sub` (идентификатор пациента), `scope`, `exp` | Только в памяти процесса |
| `refresh_token` | TTL 30 дней, привязан к устройству, с ротацией при каждом обновлении | Keychain (iOS) / Android Keystore |

**Способ передачи токена.** Заголовок `Authorization: Bearer <access_token>`. В URL, query-параметрах и cookie токен не передаётся. В логах значение заголовка маскируется.

**Проверка.** Публичные ключи для проверки подписи API Gateway забирает у Identity Provider по эндпоинту `/.well-known/jwks.json` при старте и обновляет раз в 10 минут — независимо от входа пациента. Каждый запрос проверяется по этому локальному кэшу: подпись, `exp`, `iss`, `aud` и `scope`. Обращение к Identity Provider на каждый запрос не выполняется, иначе он становится единой точкой отказа.

## 2. Политики Rate Limiting

Лимиты настраиваются на API Gateway; счётчики хранятся в Redis, общем для всех экземпляров шлюза.

| Тип запроса | Лимит | Действие при превышении |
|---|---|---|
| Публичный «Поиск врачей»: `GET /api/v1/doctors`, `GET /api/v1/doctors/{id}/slots` — без токена | 30 запросов в минуту на связку IP-адрес + идентификатор устройства (`X-Device-Id`), алгоритм Sliding Window. Второй рубеж на WAF: 300 запросов в минуту на подсеть /24 | `429 Too Many Requests` с заголовками `Retry-After: 30` и `X-RateLimit-Limit / Remaining / Reset`. Ответ формирует шлюз, до сервиса расписания запрос не доходит. При систематическом превышении источник блокируется на CDN/WAF на 15 минут |
| Авторизованное «Создание записи к врачу»: `POST /api/v1/appointments` — с access-токеном | 10 запросов в минуту на пациента (ключ — claim `sub`), алгоритм Token Bucket с всплеском до 5 запросов подряд | `429 Too Many Requests` с `Retry-After: 60`. Повторная отправка того же `Idempotency-Key` токен не расходует и возвращает сохранённый ответ операции, поэтому пациент, нажавший «Записаться» дважды, отказа не получает |

## 3. Меры защиты каналов передачи данных

1. **mTLS во внутреннем контуре** — между API Gateway и сервисами и между сервисами. Сертификаты короткоживущие (24 часа), выпускаются и ротируются автоматически через cert-manager/Vault.
2. **Защищённые каналы к легаси- и внешним системам**: HTTP-шлюз «1С: Полисы» и SOAP-интерфейс LIS — по HTTPS с проверкой сертификата, загрузка с анализаторов — SFTP/FTPS вместо FTP, webhook платёжного шлюза — с проверкой подписи запроса и по списку разрешённых адресов.
3. **Шифрование внутренних транспортов и хранилищ**: TLS для Kafka, TLS для RabbitMQ, шифрование данных при хранении в PostgreSQL и объектном хранилище; PDF-отчёты выдаются по подписанным ссылкам с TTL 5 минут.
4. **Защита периметра**: CDN с защитой от DDoS → WAF с правилами OWASP (блокировка SQL-инъекций, INT-006) → API Gateway (проверка JWT, rate limiting) → сервисы (mTLS, таймауты, Circuit Breaker). Внутренние системы публичных адресов не имеют.
5. **Гигиена данных в канале**: персональные и медицинские данные и токены не передаются в URL и query-параметрах; push-уведомления не содержат медицинского содержания; чувствительные поля маскируются в логах и трассировке.
